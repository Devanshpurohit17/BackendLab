## Part A

### 1. What is `jsonb` in PostgreSQL, and how does it differ from `json`?

Both types store JSON documents and both reject invalid JSON, but they store it differently. The `json` type keeps an exact copy of the text that was inserted, including spaces, key order and duplicate keys. Whenever a query needs one value, PostgreSQL has to parse that text again. The `jsonb` type converts the document into a decomposed binary format while inserting it. Extra spaces and key order are not preserved, and if a key is repeated only its last value is kept.

This makes writing `jsonb` slightly slower because of the conversion step. Reading is usually faster, since a key can be found without parsing the whole document again. `jsonb` also supports containment (`@>`) and key-exists (`?`) operators and can have a GIN index on the whole column, while `json` has no such operators and can only use an expression index on a particular extracted value. For most applications that search inside documents, `jsonb` is the better choice. The `json` type is useful when the original text must be kept exactly, such as for a log of received requests.

```sql
SELECT '{"a": 1, "a": 2}'::json  AS j,   -- {"a": 1, "a": 2}
       '{"a": 1, "a": 2}'::jsonb AS jb;  -- {"a": 2}
```

### 2. How can PostgreSQL work as both a SQL and a NoSQL database in the same table?

A table can have normal typed columns for facts that every row shares, and one `jsonb` column for facts that change from row to row. In a product table, every product has an id, a name, a category and a price. These belong in relational columns because the database can then enforce data types, `NOT NULL`, `CHECK` and foreign key rules. The remaining attributes depend on the product: a book has an author and pages, while a laptop has RAM and a CPU. Creating a column for each possible attribute would leave many empty values, so they are stored as a document.

A single query can use both parts. It can filter by the numeric price column and also by a key inside the document, then join the result to an orders table. Both parts are also saved in the same transaction, so an update cannot leave one half changed. The limitation is that PostgreSQL does not check the keys inside the document by default. Important fields should therefore be kept as real columns, or protected using a `CHECK` constraint.

```sql
CREATE TABLE products (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price NUMERIC(10,2) NOT NULL CHECK (price >= 0),
    attributes JSONB
);
SELECT name FROM products WHERE price < 1000 AND attributes ->> 'color' = 'black';
```

### 3. Give an example query using `->`, `->>`, `@>` and `?`, with the value returned.

The examples use the product ProBook 14, whose attributes are `{"ram_gb": 16, "cpu": "Ryzen 7"}`.

The `->` operator returns the value of a key as `jsonb`. Because the result is still JSON, a string is shown with its double quotes, and another JSON operator can be applied to it. This is useful for moving through nested objects. The `->>` operator returns the same value as ordinary `text`, so there are no quotes and it can be compared with a normal string. Numbers also come back as text, so they must be cast, for example with `::int`, before a numeric comparison.

The `@>` operator checks whether the document on the left contains the document on the right, and returns true or false. The `?` operator checks whether a string exists as a top-level key and also returns a boolean. It does not look at the value of that key, so it is useful for finding which products have a particular attribute.

```sql
SELECT attributes -> 'cpu'                 FROM products WHERE name = 'ProBook 14';  -- "Ryzen 7" (jsonb)
SELECT attributes ->> 'cpu'                FROM products WHERE name = 'ProBook 14';  -- Ryzen 7 (text)
SELECT attributes @> '{"ram_gb": 16}'      FROM products WHERE name = 'ProBook 14';  -- true
SELECT attributes ? 'author'               FROM products WHERE name = 'ProBook 14';  -- false
```

### 4. How can a GIN index on a `jsonb` column change query performance?

GIN means Generalized Inverted Index. Instead of storing one entry for each row, it stores the keys and values found inside the documents, and for each of them it remembers which rows contain it. Without this index, PostgreSQL must read every row and examine its document. With the index, it can find matching rows directly and then recheck them. The benefit grows with the size of the table. It is not visible with five rows, where reading the whole table is cheaper, which is why the planner chose a sequential scan in Task 6 until sequential scans were disabled.

The default operator class, `jsonb_ops`, speeds up containment and key-exists queries. It does not help a range comparison on an extracted value, because `->>` with a cast is an ordinary expression and not an indexed GIN operator. A B-tree expression index is suitable for that. GIN indexes also use disk space and make inserts and updates slower, so they should be created only when such searches are common.

```sql
CREATE INDEX idx_attr ON products USING GIN (attributes);
SELECT name FROM products WHERE attributes @> '{"wireless": true}';        -- can use the index
SELECT name FROM products WHERE (attributes ->> 'ram_gb')::int >= 16;      -- cannot use it
```

### 5. Where could PostgreSQL + `jsonb` replace MongoDB, and where is MongoDB the better fit?

PostgreSQL with `jsonb` can replace MongoDB when most of the data is related and only some of it is flexible. An online shop is an example: orders, customers and payments are relational, while product attributes vary. PostgreSQL gives ACID transactions across many tables as normal behaviour. MongoDB also supports multi-document transactions, but its design encourages keeping related data in one document. Joins are another strength of PostgreSQL, since SQL joins are flexible and well optimized, whereas MongoDB uses `$lookup` in an aggregation pipeline.

For schema enforcement, PostgreSQL has types, foreign keys and constraints for its columns, but the inside of a `jsonb` value needs extra checks. MongoDB can validate documents using JSON Schema rules, but it does not have foreign keys. MongoDB is the better fit when nearly all data is made of independent documents and the volume needs many servers, because sharding is built in. PostgreSQL can scale reads using replicas, but spreading writes normally needs an extension such as Citus or work in the application. The choice should depend on relationships and scale, and not only on whether the data is JSON.

```sql
BEGIN;
UPDATE products SET attributes = jsonb_set(attributes, '{stock}', '4') WHERE id = 5;
INSERT INTO orders (product_id, quantity) VALUES (5, 1);
COMMIT;
```

// Task 7: the same products and queries in MongoDB
const { MongoClient } = require("mongodb");
const client = new MongoClient(process.env.MONGO_URL || "mongodb://127.0.0.1:27017");

async function main() {
  const products = client.db("backend_assignment2").collection("products");
  await products.deleteMany({});
  await products.insertMany([
    { name: "Clean Code", category: "book", price: 499, attributes: { author: "Robert C. Martin", pages: 464 } },
    { name: "Eloquent JavaScript", category: "book", price: 650, attributes: { author: "Marijn Haverbeke", pages: 472 } },
    { name: "ProBook 14", category: "laptop", price: 72000, attributes: { ram_gb: 16, cpu: "Ryzen 7" } },
    { name: "LiteBook 13", category: "laptop", price: 41000, attributes: { ram_gb: 8, cpu: "Core i3" } },
    { name: "Wireless Mouse", category: "accessory", price: 899, attributes: { color: "black", wireless: true } },
  ]);
  await products.createIndex({ "attributes.ram_gb": 1 });

  const names = async (filter) => (await products.find(filter).toArray()).map((p) => p.name);
  console.log("Books over 470 pages:", await names({ category: "book", "attributes.pages": { $gt: 470 } }));
  console.log("Laptops 16GB+:", await names({ category: "laptop", "attributes.ram_gb": { $gte: 16 } }));
  console.log("Black accessories:", await names({ category: "accessory", "attributes.color": "black" }));
  console.log("Wireless:", await names({ "attributes.wireless": true }));
}

main()
  .catch((error) => { console.error(error.message); process.exitCode = 1; })
  .finally(() => client.close());
